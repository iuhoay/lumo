# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lumo is a macOS text tool in two coupled parts:

- `Lumo.popclipext/` — a thin PopClip extension. A text action builds a
  `lumo://translate?mode=…` URL (clipboard handoff when text > 6000 chars) and
  hands off to the app. No LLM logic lives here.
- `mac-app/` — the native menu-bar app (SwiftUI/AppKit, `LSUIElement`, no Dock
  icon). Does all LLM calls, streaming, history, TTS, and Sparkle auto-update.

## Build

The Xcode project is generated by XcodeGen from `mac-app/project.yml` — **edit
`project.yml`, never `Lumo.xcodeproj`** (the `.xcodeproj` is gitignored and
regenerated). After any change to `project.yml`:

```sh
cd mac-app && xcodegen generate
```

Universal release build (what CI runs; the build number must be the git commit
count or Sparkle won't see a newer build):

```sh
cd mac-app
xcodebuild -project Lumo.xcodeproj -target Lumo -configuration Release \
  SYMROOT="$PWD/build" ARCHS="arm64 x86_64" ONLY_ACTIVE_ARCH=NO \
  CURRENT_PROJECT_VERSION="$(git rev-list --count HEAD)" build
```

The Debug config builds a separate, coexisting "Lumo Dev" app
(`com.iuhoay.lumo.dev`, `lumo-dev://`) so it never collides with the release
build's URL-scheme routing. Set the PopClip extension's "App URL Scheme" option
to `lumo-dev` to test against it.

There are no automated tests.

## Signing & auto-update (don't "fix" these)

- The app is **ad-hoc signed** (`CODE_SIGN_IDENTITY = "-"`), no Developer ID or
  notarization. `CODE_SIGNING_ALLOWED` is `YES` (not `NO`) on purpose: Xcode
  must sign the embedded `Sparkle.framework` and its nested XPC services
  inside-out during the build. `codesign --deep` after the fact mis-signs them
  and Sparkle's helpers then refuse to run.
- Updates are verified with **EdDSA** (`SUPublicEDKey` in `project.yml`); the
  private key is the CI secret `SPARKLE_PRIVATE_KEY`.
- `CFBundleVersion` comes from `CURRENT_PROJECT_VERSION` = git commit count.
  Keep it monotonic or Sparkle stops detecting updates.

## Releasing

CI (`.github/workflows/release.yml`) builds, EdDSA-signs, generates
`appcast.xml`, and publishes the GitHub Release **on push of a `v*` tag**. The
actual logic lives in **`bin/release`** (`build` / `appcast` / `publish`
subcommands); the workflow just calls each one. Edit `bin/release`, not the
inline YAML, and shellcheck it. Before tagging:

1. Bump the version in **both** places in `mac-app/project.yml`:
   `MARKETING_VERSION` and `info.properties.CFBundleShortVersionString`.
2. Move `CHANGELOG.md`'s `## [Unreleased]` into a dated `## [X.Y.Z] - YYYY-MM-DD`
   section (Keep a Changelog format). `scripts/release_notes.py` extracts this
   section by its `[X.Y.Z]` heading for the release body and the Sparkle
   appcast, so the heading must match the tag.
3. Commit the bump on a release branch and merge it via PR — **direct pushes to
   `main` are rejected by a branch ruleset** (`GH013`). Only after the release
   commit lands on `main`, tag that commit and push the tag (tags bypass the
   ruleset and the tag push is what triggers CI):
   `git tag vX.Y.Z <merged-sha> && git push origin vX.Y.Z`. Tagging before the
   commit is on `main` leaves the tag pointing off-`main`.

The `/release` skill does steps 1–3.

## Localization

Ships English (base) + Simplified Chinese (`zh-Hans`). User-facing strings live
in two places — update both:

- App: `mac-app/Lumo/Localizable.xcstrings`.
- Extension: title/label/description fields in `Lumo.popclipext/Config.json` and
  `translate.js` use `{ "en": "…", "zh-Hans": "…" }` dictionaries.

Adding a language also means updating `CFBundleLocalizations` in `project.yml`.
